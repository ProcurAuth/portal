Documentation

Each page has one purpose. Start with the overview, then follow the guides in the order that you need them.

Start

Overview

portal is one Rust program for a lab or a small organisation. It opens sessions for people and protects the web services behind Traefik.

Getting started

This page takes you from a clean machine to a portal that works, in about five minutes. Docker is the only tool that you need. The first path runs the portal alone.

Architecture

This page shows the parts of portal, its three listeners, the path of a request, and the layout of the repository.

Use

Authentication and sessions

This page describes how a person authenticates to the portal and how the portal keeps the session.

Grants and the gate

A grant lets a user or a key do one action on one node of a service. The gate checks the grant access on each request that Traefik sends to portal.

Identity tokens and the PDP

portal gives an identity token to each service that a user or a key can reach. It also answers the questions of the services about grants, as an AuthZEN policy decision point (PDP).

Keys and limits

A key lets a program call a service for a user. A key never has more rights than its owner. A grant can also hold limits: ceilings that the service applies, and budgets that the PDP counts.

Launcher and service discovery

The launcher is the home page of the portal. It shows one tile for each service that the signed-in person can open. A service declares itself with labels or annotations, and the portal finds it.

Settings pages and history

The settings pages are where the superadmin manages accounts, services and keys, and where it reads the history. An account that is not the superadmin sees only the tabs that its permissions open.

Several instances (PostgreSQL)

By default, one process owns a SQLite file, and only one instance can be active. The optional postgres block moves all data to a shared PostgreSQL database.

Traefik and TLS

portal knows nothing about TLS. Traefik terminates TLS and calls portal for each request that needs a decision. This page lists the duties of the deployment in Traefik.

Inbox

The Inbox is a feature of the portal. It sends alerts to Android phones and makes sure that each subscribed phone shows each alert one time.

Inbox: agents

This chapter tells how an agent uses the portal. An agent is a program that asks a person to approve an action, or to answer. The person is the owner of the key that the agent uses.

Inbox: Android app

The Android app Portal Inbox receives the alerts of one or more portals. It also lets the owner answer the approvals and the questions of agents.

Inbox: phone protocol

This page describes the protocol between the Inbox of the portal and the Android app Portal Inbox: enrollment, the Noise session, and the frames. It is for the author of a client or of a test.

Inbox: configuration rules

This page gives the rules of the block inbox that the table of keys cannot show. It tells which blocks go together, which keys have no default, and which keys contradict each other.

Inbox: security model

The Inbox carries alerts that can be vital. This page gives the security model of the Inbox: what it protects, how, and what it does not cover.

Inbox: requirements

This document states what the Inbox must do and why. The Inbox is a feature of the portal. The code is the reference for details. The design page gives the reasons for the main choices.

Configure and operate

Configuration

The portal reads one HCL file. The file is the only source of the configuration, and the program checks it before it serves.

Security model

This page states what the portal protects, who it trusts and which rules the code keeps. It also lists the known limits of a deployment and the measures that remove them.

Operations

This page is for the operator of a portal. It covers start and stop, backups, the rotation of a key, the metrics to watch and the commands of the binary. It also gives the notes for each upgrade.

Build and release

This page tells how to build the portal, its image and the Android app, how the dependencies stay fixed, and how a release is made. A release ships binaries, the APK and the source.

Development

This page is for a person who changes the code or the documents of this repository. It gives the rules of a change, the checks and the test scripts with their variables.

Reference

Reference

This page lists the HTTP endpoints of the three listeners of portal. It lists the error codes, the cookies, the headers and the exit codes.

Limitations

This page lists what portal does not do, and the limits that its design sets. Each item gives the fact, its consequence and a way to work with it.

Design: the Inbox

The Inbox is the part of the portal that sends alerts, questions and approvals to Android phones. This page gives the design choices and the reason for each one.

Design: sign-in protection

This page explains why the sign-in page of the portal behaves as it does. It states what each measure stops, what it does not stop, and how the tests check it.

Changelog

This file lists the notable changes of each release of portal. The layout follows Keep a Changelog. The version numbers follow SemVer. The date is the date of the tag.
